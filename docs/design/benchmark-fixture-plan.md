# Benchmark fixture plan

- Status: **proposed**. For handoff HO-ANA-20261110-9Q72. Companion to the [design note](segment-retrieval-and-claim-recurrence.md).
- **Synthetic text only.** Every fixture is written from scratch for this repo. No real conversation, export, title or quote is copied, paraphrased or used as a template. The "hockey thread" is named only as the *kind* of case Zach described [Zach]; its content is not known to this author and is not reproduced.

## Shared format (proposed)

Each fixture is a directory `fixtures/<id>/` with:

| file | contents |
|---|---|
| `conversation.json` | a minimal ChatGPT-export-shaped mapping (nodes, parents, children, `current_node`), so the rescued offline core parses it into message units unchanged |
| `gold.json` | the labels each layer is scored against (below) |
| `README.md` | what the fixture tests, which failure it reproduces, and which design rule should catch it |

`gold.json` fields:

- `objectives`: the retrieval objectives to run, with ids;
- `anchors`: per objective, the unit ids that should be found;
- `islands`: gold segments as `[first_unit, last_unit]` on a named branch path;
- `placements`: island → one of `core | ancestor | application | conflict | rejection | adjacency`;
- `evidence`: per unit span, the expected `speaker`, `artifact_class`, `local_stance`, `acceptance_status`, `canonical_eligibility`;
- `claims`: expected claims after round 0 and after recurrence, with expected status and expected operations;
- `must_not`: things that must never appear (a claim text, a merge, a chronology order, a cross-unit quote).

Fixtures are generated by a small script from a readable outline, so a reviewer edits the outline, not the JSON.

## F-00: the buried branch (synthetic analogue of the hockey thread)

What Zach described [Zach]: a conversation whose title and dominant topic are unrelated to the target, holding a valuable conceptual branch. The test: can Anamnesis recover a specific conceptual branch from a conversation whose title gives no clue?

Synthetic design:

- **Title:** "Fixing the garden irrigation timer". **Dominant topic:** about 40 turns on drip-line pressure, a valve schedule and a leaking connector.
- **Buried branch:** turns 17–23. A passing remark about how water finds paths no one planned turns into the user developing an idea about *emergent routing in a team's task queue*: the user states a definition (U-19), the assistant proposes an extension (A-20), the user accepts part of it and rejects the rest (U-21), and the user names the idea (U-23).
- **A second, separate island:** turns 34–35, where the user refers back to the named idea in one sentence. It must come back as **its own segment**, not merged with 17–23 because they share a conversation.
- **Distractors:** the word "routing" also appears in the irrigation discussion (turns 5, 28), in the plumbing sense. These should anchor on lexical search and be placed `adjacency`, not `core`.
- **An alternate:** turn 20 has a regenerated-away sibling (A-20′) where the assistant proposes a different name. Text unique to A-20′ must be findable (`alternate`), and A-20′ must never be merged into the 17–23 segment of the active branch.

Scores: anchor recall on the target objective; IoU for both islands; segment distinctness = 2 islands, 0 cross-island merges; distractors placed `adjacency`; the user's definition (U-19) and name (U-23) become `core` claims; the rejected part of A-20 does not.

## F-00b: the buried branch with no shared words (added after the stress test)

Same shape as F-00, but the buried branch never uses the seed query's terms: the user talks about "how the work finds its own way through the team" and names the idea with an invented word. The seed objective uses the target concept's ordinary words.

- Lexical-only anchor discovery is **expected to fail** this fixture. It is recorded as an expected failure, so it marks the point where a semantic or term-expansion anchor source (via `resolve_term` objectives) has to earn its place.
- This is closer to the real difficulty Zach described than F-00: the passage is hard to find because nothing on its surface points at it.

## Regression fixtures for the 2026-08 failures

Each reproduces one failure from the thread [thread], in synthetic form, and names the design rule expected to catch it.

### F-01: layer conflation

- Synthetic setup: the user defines a three-tier scheme with invented names ("Hearthstone / Lantern / Beacon"), states that Lantern is *not* a tier but a role inside Hearthstone, and later says an external "Cloud" service is a backend, not a tier. An assistant reply in between lists four tiers, including Cloud, and merges Hearthstone and Lantern.
- Failure to reproduce: claims that treat the assistant's four-tier list as the scheme.
- Should be caught by: the adversarial terminology pass (design §5 rule 7) resolving each tier name against `user_statement` evidence; the conflicting assistant reply gives `MARK_CONFLICTING`, not `EXPLICIT`.
- `must_not`: a `core` claim stating four tiers; a `core` claim treating Lantern as a tier.

### F-02: invented chronology

- Synthetic setup: three conversations with timestamps T1 < T2 < T3, where the user's position changes (A at T1, B at T3). Fixture evidence ids are deliberately assigned in the reverse order (the T3 unit gets the lowest evidence number).
- Failure to reproduce: a narrative that orders events by evidence number ("first B, then A").
- Should be caught by: design §3.6 / §5 rule 9 (chronology only from unit timestamps and branch order).
- `must_not`: any claim or timeline that puts B before A.

### F-03: rejected external draft becomes canon

- Synthetic setup: the user pastes a long draft "from another assistant" proposing a specific architecture, then says in the next turn that they reject two of its three points and keep one.
- Failure to reproduce: the draft's rejected points appear as `core` claims because the text sits in a user message.
- Should be caught by: `artifact_class: imported_draft` and `acceptance_status` (design §4 rules 1–2). Only the accepted point is eligible; the rejected points are placed `rejection` and their rationale is recoverable by a `recover_rejection` objective.
- `must_not`: a `core` claim stating either rejected point.

### F-04: instruction echo as a claim

- Synthetic setup: the run's own retrieval or reconstruction prompt (for example "Reconstruct the user's full model of X, preserving all nuance") appears inside the corpus, because the user once pasted a prompt into a conversation. It contains the target terms densely, so it ranks highly.
- Failure to reproduce: the top claim is a restatement of the instruction.
- Should be caught by: `artifact_class: instruction`, never eligible, never a claim on its own (design §4 rule 3).
- `must_not`: any claim whose only support is the instruction unit.

### F-05: preserved bad baseline

- Synthetic setup: a round-0 ledger supplied as a fixture input (not generated), with 6 claims of which 3 are wrong: one cites an irrelevant passage (low overlap), one cites a quote that does not occur verbatim, one is contradicted by a later user statement in the corpus. Recurrence then has objectives that retrieve the contradicting statement.
- Failure to reproduce: 6 claims in, 6 out, 0 revisions; guard findings reported but no downgrades.
- Should be caught by: the quote guard writing `WEAKEN` revisions (design §5 rule 6) for the first two; `MARK_CONFLICTING` for the third; and, if a variant run disables the guard, the inert-recurrence flag (rule 8).
- `must_not`: the three wrong claims still `EXPLICIT` after one round.

### F-06: good baseline must survive (the reverse of F-05)

- Synthetic setup: a round-0 ledger of 6 correct claims whose citations legitimately paraphrase or abstract the source (low word overlap, right meaning), and a recurrence round that retrieves only consistent evidence.
- Failure to catch: the quote guard over-correcting, downgrading correct claims so the ledger decays to `UNRESOLVED`.
- Scores: false-downgrade rate (target 0 here); the threshold is tuned on F-05 and F-06 together, never on F-05 alone.

### Authorship and coverage

- At least one of F-01 to F-05 is written **blind** by Kate or a fresh-context agent from the failure description in this file alone, so the fixtures are not only the design author's idea of the failure.
- Not covered yet: tool or code output as evidence, contradictions across many conversations, very long single turns, multimodal content. Listed so they are not mistaken for passed.

## Fixtures for the three stage-4 gaps

These already exist as gap probes in the private round-trip check (`roundtrip_check.py`, 2026-11-09). Port them here as F-10 (hit resolves to a unit), F-11 (alternate-only text is findable and labelled), F-12 (no evidence link or snippet spans two speakers), keeping their synthetic text.

## Order of work (proposed)

0. A deliberately naive baseline (conversation-level hits, no expansion, no guard) that must **fail** every regression fixture, to show the fixtures discriminate.
1. Fixture generator and `gold.json` schema, with F-00, F-00b and F-10–F-12 (they test retrieval and segmentation, which need no model).
2. The validators the regression fixtures exercise: quote guard that writes revisions, eligibility rules, chronology rule, inert-recurrence flag. Each fixture first fails against a deliberately naive baseline, then passes.
3. F-01 to F-06.
4. Only then any model-driven stage (distillation, placement), scored layer by layer.

Step 2 is the stop point the dissent review names: if the validators can't be made to fail and then pass the regression fixtures, revisit the design before building further.
